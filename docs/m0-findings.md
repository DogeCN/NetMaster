# M0 平台核验结论

日期：2026-10-02。探针：`m0/`（worker `netmaster-m0`，CI 驱动，运行记录见 GitHub Actions
`m0-probe` workflow，产物 `m0-drive-results`）。**2026-10-03 注：探针与 workflow 已删除**，
本档即最终结论；如需复核，按各节"实验"描述重建探针即可。

同日第二轮（E6-E9）：探针仍是 `netmaster-m0`，其中直连出口与 20 并发流的结论在**真实
部署的 `netmaster` worker** 上复验过。E5 没有独立小节——它是 E4 的一个变体（见 E4 正文）。

结论先行：**九项实验中四项推翻了 PRD v1.1 的关键假设**（E1、E3、E6、E9），两项的前提
在 2026 年失效（E7 的目标选型、E8 的预算模型），一项不成立但结论有利（E4），一项成立（E2）——

| # | PRD 假设 | 实测结论 | 判定 |
|---|---|---|---|
| E1 | 入站 WS 消息按 20:1 折算请求量 | **≈1:1 计入请求**，未观察到任何折算 | ❌ 推翻 |
| E2 | DO 内并发出站连接上限语义需确认 | 单 DO 12 条并发 `connect()` 全部成功（worker 内同） | ✅ 成立 |
| E3 | `connect()` 可拨 IPv6（NAT64 的前提） | **IPv6 出站不支持**，一律立即失败 | ❌ 推翻 |
| E4 | DO 休眠期间出站流保活 | **有出站 socket 的 DO 不休眠**；socket 存活与休眠互斥；空闲 socket 由对端关闭 | ⚠️ 假设不成立但结论有利 |
| E6 | 直连出口可以用明文 HTTP 目标（`:80`） | **端口 80 一律被平台拒绝**（<2ms），域名与 IP 字面量同样被拒 | ❌ 推翻 |
| E7 | 只要目标不在 CF 网段就能直连 | 规则成立，但 **example.com 在 2026 年已解析到 CF IP**：所有拿它当"非 CF 直连目标"的样例失效 | ⚠️ 规则成立，选型前提失效 |
| E8 | 单次 invocation 的 50 个子请求足够 mux 稳态 | **DO 激活期内所有 WS 消息共享这一份预算**，第 26 对 `fetch(DoH)+connect` 精确耗尽 | ⚠️ 假设不成立，对策已实现 |
| E9 | `wrangler tail` 能看到 DO 的 `console` 输出（诊断手段） | **DO 的 console 输出在 tail 上不可见**，只有 DO 间 `fetch` 调用可见 | ❌ 推翻 |

按 PRD §14 的风险门，E1、E3 两项不成立 → 暂停 M1 实施，先修订架构（建议见文末）。
第二轮的 E6-E9 是在 M0 关闭、M1-M5 已实施之后测到的，没有再走风险门：对策已写进实现
（见文末"第二轮实测的补充修订"），PRD 的回写由主会话统一处理。

## E1：WS 消息计费折算

实验：客户端向 Hibernation DO 发送精确数量的消息，SQLite 持久计数器累计
（upgrade +1、每条消息 +1、close +1），再用 GraphQL analytics
（`durableObjectsInvocationsAdaptiveGroups`）对照账户级请求数。

实测：

- 计数器逐轮 delta 与发送量严格相等：+102（1 upgrade + 100 msg + 1 close）、+50。
- 消静置 40s 后再发，消息照常送达且计数照常累计 → Hibernation 唤醒与计数均正常。
- 13:00-14:00 UTC 整点桶：**829 requests**；其余时段 0（归属干净）。三次完整实验
  发出的 DO 可见事件（含出站回包）总量与 829 同数量级、明显接近 1:1 而非 1/20。
  若 20:1 成立，该数字应在 ~75 而不是 829。

结论：**WS 消息按 1:1（或更差，若出站帧也计费）计入每日 10 万请求配额**。对协议的
影响：多路复用省下的只是 WS 建连成本，每帧仍是一条请求。个人规模（每天数千到数万帧）
在 10 万/日之内，但"mux 摊薄请求量"的叙事不成立，协议帧数要吝啬（合并小包、避免
逐帧心跳）。

## E2：单 DO 内并发出站连接

实验：单 DO 与单 worker 内各并发 12 条 `connect()`（8.8.8.8:443）。

实测：**12/12 成功**（DO 与 worker 均是），延迟个位数毫秒。

结论：文档中"每请求 6 条出站连接"的限制不适用于 DO 内 TCP socket；PRD 的 6 槽位
竞速是设计选择（预算控制）而非性能天花板，mux 稳态不会撞上限。

## E3：IPv6 / NAT64 出站

实验：拨 IPv4 对照组（8.8.8.8:443 成功，4ms）、IPv6 字面量（2001:4860:4860::8888 的
443/853）、CF IPv6（2606:4700:4700::1111）、NAT64 合成地址（2a00:1098:2b::808:808:53）。

实测：**所有 IPv6 目标一律立即失败**（"cannot connect to the specified address"，
<2ms，连拨号都没发生）。IPv4 全通；DoH（fetch 到 cloudflare-dns.com）正常。

2026-10-02 复核（用户要求排除前缀因素）：补测 level66 `2001:67c:2960:6464::/96`、
well-known `64:ff9b::/96`、Trex `2001:67c:2b::/96`、nat64.net `2a00:1098:2b::/96`
四个前缀的合成地址（`::808:808`，443/53），以及裸 IPv6（Google `2001:4860:4860::8888`
53/853、CF `2606:4700:4700::1111` 443）——**全部同样 <2ms 失败**，与 IPv4 对照组
（8.8.8.8:443，4ms 成功）形成鲜明对比。结论不变：不是前缀选择问题。

结论：**Workers `connect()` 仅支持 IPv4 出站，IPv6 字面量与 NAT64 合成地址均不可用**。
PRD §7.4 的 NAT64 出口（其全部价值就在绕开 connect() 禁连 CF 网段）在该平台上无法
实现，不是调参问题，是运行时能力缺失。已定稿：砍 NAT64（用户 2026-10-02 批准）。

## E4：出站 socket 与休眠/驱逐

实验：DO 内开 TCP socket（带后台读循环），客户端静置 75s，期间 Alarm 在 +20s 触发，
随后检查 socket 状态；E5 变体：客户端断开 WS 后等 45s，新 WS 连回同一 DO 检查。

实测：

- Alarm 在 +20s 触发时 `instanceSockets` 仍非空、isolate 未换 → **开着出站 socket 的
  DO 不会被休眠**（挂起的 socket I/O 阻止休眠）；E5 中客户端断开 45s 后 DO 同样未驱逐。
- socket 的死亡全部来自**对端空闲超时**（Quad9 :53 与 tcpbin :4242 都在数十秒内关闭
  空闲连接）：读端 EOF、写端 `WritableStream has been closed`。
- 没有观察到"运行时在休眠/驱逐时杀 socket"——因为根本到不了休眠那一步。

结论：PRD §4.6"休眠期间流保活"的对象不存在：**socket 存活期间 DO 必然醒着**（计 DO
时长），socket 关闭后休眠才有意义。设计含义：
1. 有在途流时 DO 醒着是必要的，无需对抗；
2. 空闲多路复用连接的出站流会被对端掐掉，协议层要有每流死亡的正常处理（已有 CLOSE）；
3. 零流的空闲 WS 走 Hibernation 不驻留内存——这正是 PRD 预期的形态，成立。

## E6：端口 80 禁拨

实验：`connect()` 拨明文 HTTP 目标（example.com:80）、同一端口的 IP 字面量
（1.0.0.1:80），同期用 8.8.8.8:443 做对照。探针 `netmaster-m0`。

实测：

- example.com:80 与 1.0.0.1:80 **都在 <2ms 内被拒**，错误信息是
  *"It looks like you might be trying to connect to a HTTP-based service — consider
  using fetch instead"*；连拨号都没发生，与 E3 的 IPv6 失败形态一致。
- 同期 8.8.8.8:443 **正常，5ms**。
- 这条规则与"CF 网段禁连"**相互独立**：1.0.0.1 既不在 CF 公布的任何网段里，也不在我们
  自己的禁连清单里（`PRIVATE_V4` 没有 `1.0.0.0/8`），照样被平台拒——而探针是直接调
  `connect()`、不经过我们的代码。也就是说这次拒绝来自平台层，与 CF 网段规则无关。

结论：**`connect()` 拨 80 端口一律失败，与目标是不是域名、是不是 CF 网段无关**。设计含义：

1. **直连出口只对非 80 端口有效**。PRD 与文档里所有"直连 example.com:80 验证 curl 经
   代理访问 HTTP"的验收口径作废：明文 HTTP 目标在直连路径上不可达。验收要改成 443 +
   客户端做 TLS（客户端侧的 TLS 是端到端的，代理只搬运密文）。
2. **ProxyIP 路径不受这条影响**：Worker 拨的是中继的 443，隧道里目标端口只出现在
   `CONNECT host:port` 请求行里，从不经过 `connect()`。所以"CF 托管目标走 ProxyIP"与
   目标端口无关（这一点值得写清楚，否则很容易把 E6 误读成"整个 TCP 代理不能用 80"）。
3. **平台的错误文案具有误导性**：它建议"改用 fetch"，而这里真正的原因是端口被禁。
   排障时不要被这句话带偏去改协议——它是死路，fetch 只能拿 HTTP 响应、拿不到字节流。
4. 实现现状与取舍：`isForbidden()` 目前只拦端口 25 与私网/CF 网段，**没有把 80 列入
   禁连**，所以客户端请求 80 端口会真实拨一次、白烧一个子请求（按 E8 计费）才拿到
   0x03。提前拒绝能省一次注定失败的拨号，属主会话的取舍，本节只记录事实。

## E7：CF 网段拒绝的签名与目标选型

实验：`connect()` 拨解析结果落在 CF 网段的 IP（example.com 当前解析结果、
www.cloudflare.com），与 E6 的失败形态对照。

实测：

- 报**与 E6 相同的错误文案**，**<20ms** 返回；不是超时、不是握手失败。
- **example.com 在 2026 年已经是 CF 托管**——解析出的 A 记录落在 CF 网段内。
  "找个非 CF 的域名做直连验收目标"这个做法本身失效了。

结论：CF 网段禁连与 E6 是两条独立规则，但**错误文案完全一样**，所以只看错误信息无法
区分"端口被禁"和"目标在 CF 网段"，必须自己解析并比对网段。设计含义：

1. **直连可行性判定必须建立在解析后的 IP 上**，而不是域名本身。实现上直连路径已经
   是"先 DoH 解析出 A 记录、再逐个 IP 拨号"，所以判定点天然在 IP 层
   （`exits.js` 的 `resolve4()` / `directConnect()`）。
2. **目标选型教训**：文档、测试与验收脚本不能再拿 example.com 当"非 CF 直连目标"的
   样例。已改：`client/internal/outbound/live_test.go` 与 `server/test/e2e.mjs`
   （第 3/4 项的直连目标改成 `www.google.com:443`、CF 托管目标改成
   `www.cloudflare.com:443`，两者都走 443，客户端做 TLS）。连带回写（2026-10-03）：
   各文档的 `example.com:80` 日志样例、`selector.go` 里客户端首连通验证 `Verify()` 的
   目标（原为 `example.com:80`，在真实部署上必失败）以及 `docs/PRD.md` 的对应表述。
3. 一个合格的"直连验收目标"必须**同时**满足：解析结果不在 CF 网段 **且** 端口不是 80。
   只满足一条就会得到一个看似是平台故障、实际是选型错误的 0x03。
4. 顺带澄清一处实现注释的越界：`exits.js` 头部写着"`connect()` 只接受 IP 字面量——
   域名目标被平台直接拒绝（consider using fetch）"。E6/E7 的数据**并不能证明域名被拒**
   （两个失败样本都在 80 端口上，域名与 443 的组合没有单独测过）。实现先把域名解析成 IP
   无论如何都是稳妥的，但那句注释的因果归因超出了实测范围，按本节结论更准确的表述是
   "平台拒 80 端口；域名一律先解析成 A 记录以获得网段判定能力"。

## E8：子请求预算（50/invocation）

实验：在单次 invocation 内顺序做 `fetch(DoH)` + `connect` 配对，每对消耗 2 个子请求，
一直数到失败。同时在真实部署的 worker 上跑 20 并发流的直连测试。

实测：

- **第 26 对失败**——50 个子请求被精确耗尽。文档值 50/invocation 实锤，没有"隐藏的
  额外额度"。按每对 `fetch + connect` 各 1 个子请求算，25 对正好用满 50，第 26 对在
  额度耗尽后失败（也就是说失败发生在这一对的第一个子请求上，观测不到更多细节）。
- **DO 激活期内所有 WS 消息共享这一份预算**：20 并发流的直连测试在预算耗尽后
  **后续全部返回 0x03**，而不是新消息重新获得额度。
- 失败形态与 E3/E6 一致：平台级拒绝，客户端无法通过重试同一目标解决。

结论：免费版的 50 子请求是**每个 invocation、每个 DO 实例**的额度，而一条活跃的 WS
会话就是一次长驻 invocation，所以它实际上是**"每条连接一生"的总额度**。设计含义：

1. **预算账**：一条流的直连成本 = 1 次 `connect` +（DNS 未命中时）1 次 DoH。稳态下
   同一域名的 DoH 被缓存复用，每条新流约 1 个子请求 → 单条连接一生大约能服务
   **30-50 条流**，之后必然见底。这是设计上的续命点，不是故障。
2. **与 E2 不矛盾，两者测的不是一回事**：E2 测**并发度**（同时挂着多少条出站连接，
   12 条全成功），E8 测**累计子请求数**（这条连接一生能开多少条流）。把 E2 的结论当成
   "并发无上限"会直接撞上 E8。
3. 已实现的三条对策（代码位置已核对）：
   1. **DNS 进程内缓存**（`exits.js` 的 `dnsCache`，TTL 5 分钟）：稳态下同一域名每条
      连接只花一次 DoH；
   2. **直连失败记忆**（`session.js` 的 `directFailed`）：本连接内不再重试同一个被平台
      拒绝的目标，把失败的 dial 从预算里省掉；
   3. **计数到阈值优雅断开**（`session.js` 的 `connectCount >= 30` → `close(1000,
      "budget")`）：客户端带着等待队列重连，换一份全新预算继续。
4. **实现现状与意图的差距（供主会话判断）**：计数点在**成功建流之后**，失败的 `connect`
   （同样消耗子请求）不计入，所以"30"实际是"30 次成功出口"，最坏情况下真实消耗会高于
   预算估算。这不影响功能正确性（超了就 0x03，客户端重连），但会让"为什么这么早就
   断开"的日志数字对不上账。
5. 对客户端的硬要求：**优雅断开必须伴随重连 + 请求重放语义**，否则用户会看到随机
   断流。客户端已实现重连退避与等待队列，所以日志里出现连接重建属于正常现象。

## E9：DO 的 console 输出在 wrangler tail 上不可见

实验：Session DO 内 `console.log`/`console.error`，在 `wrangler tail` 里观察；同时观察
DO 之间 `fetch` 调用的可见性。

实测：

- **DO 的 console 输出在 tail 上完全不可见**；worker 入口（`index.js`）的 console 可见。
- **DO 之间的 `fetch` 调用可见**（带调用关系），这是 tail 里唯一能看到 DO 内部动作的信号。

结论：任何"靠 `wrangler tail` 看 Session DO 日志排障"的运维流程**无效**，而且失效得
很安静——你看到的只是一个安静的 tail。设计含义：

1. **诊断必须走 KV 通道**，已有：出口失败原因写 `debug:lastExit`
   （`session.js`）。
2. 判断"某件事到底有没有发生"要**查 KV 的时间戳**，不要查 tail。日志只用于 worker 入口
   层面的粗筛。
3. 本仓库里曾经有一个现成的例子值得警惕：`index.js` 的 `scheduled` 处理器仍调用已被
   删除的 `runCron`（`cron.js` 已删，`build.mjs` 的模块列表也已去掉）。因为
   `wrangler.toml` 的 `[triggers] crons` 已被移除，这个处理器当时是**死代码、不会触发**；
   但如果有人把触发器加回去，它会抛 `ReferenceError` 并被 `catch` 吞掉，而这条
   `console.error` 按本节结论**在 tail 上看不见**，看上去像"定时任务在正常运行"。
   这正是 E9 最典型的坑：失败静默、证据看起来是好的。（该死代码已随后清除：
   scheduled 处理器整段删除。）
4. 推论：新增诊断信息时，**默认写 KV，不要默认写 console**。

## 对 PRD v1.1 的修订建议（待定稿）

1. **砍 NAT64 出口**（E3）。CF 承载目标的出口只剩 ProxyIP 一类：`connect()` 到
   中继 → HTTP CONNECT → 隧道。竞速从 6 槽 NAT64/ProxyIP 交错简化为多 ProxyIP
   候选竞速（参数不变）；Router DO、Cron 健康检查、KV last-good-wins 全部保留，
   只是不再维护前缀池。Cron 的"剔除回指条目"逻辑保留。
2. **明确 WS 消息 1:1 计费**（E1），协议层约束写进 §10：数据帧尽量满 64KB、
   心跳走 WS 协议层 Ping（不产生 DO 消息，免费）、废除逐帧 ACK 类设计。
3. 出口层其余参数（6 槽、1.5s/3s 超时、120ms 交错）按 E2 结论保留。

> 上面这份清单是 M0 当时的记录，保留原样以便对照。其中第 1 条"Cron 健康检查全部保留"
> 后来没有按原样落地：Worker 端 Cron 因免费版只有整点触发、且实测不可靠而被撤掉，
> 出口池刷新改由 GitHub Actions 定时任务承担（见下一节）。

## 第二轮实测（E6-E9）的补充修订（已实施）

1. **验收目标一律走 443**（E6）。验收与文档样例从 `example.com:80` 改成
   `www.google.com:443` + 客户端 TLS；`client/internal/outbound/live_test.go` 与
   `server/test/e2e.mjs` 已改。`docs/` 里的旧样例与 PRD 的验收描述仍待主会话回写。
2. **直连判定基于解析后的 IP**（E7）。`exits.js` 的 `resolve4()` 用 DoH 拿 A 记录、
   进程内缓存 5 分钟，`directConnect()` 逐个 IP 拨号——网段判定因此天然落在 IP 层。
   目标选型的教训写进文档：不要再拿 example.com 当"非 CF 直连目标"。
3. **预算三条对策**（E8）：DNS 进程内缓存、直连失败记忆（本连接内）、
   `connectCount >= 30` 优雅断开让客户端重连换预算。客户端侧的重连退避与等待队列
   是这个机制成立的前提。
4. **诊断改走 KV**（E9）：`debug:lastExit` 记出口失败原因。**不依赖
   `wrangler tail` 看 DO 日志**——DO 的 console 输出在那里不可见。
5. 出口池刷新从 Worker Cron 迁到 GitHub Actions（`.github/workflows/refresh-relays.yml`），
   KV 契约（`proxyip:top` 的字段与前 4 条）不变，`last-good-wins` 语义不变。
